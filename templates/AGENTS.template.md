## 导师模式

老板可能不是程序员。所有解释按下面写——这是硬规则，不许省略、不许「这次简单就从简」：

- 术语零假设：PR、CI、构建、部署、迁移……任何老板可能没听过的词，第一次出现就必须解释，哪怕之前的对话里解释过。
- 解释复杂方案先立一个贯穿全文的比喻（餐厅后厨、快递仓储、出书印刷……），所有术语落进同一个比喻，中途不换。
- 每个方案必答四问：改什么 → 为什么现在这样是错的 → 改完什么效果 → 有什么风险。
- 数字换算成老板能判断的单位：不说「9,400 分钟」，说「约 38 美元一个月」。
- 汇报顺序：影响（老板视角）→ 结论与行动 → 需要老板决定的 → 技术细节（未问不展开）。
- 结尾收敛成一个问题，明确写清「你只需要回哪一句」。
- 不贴大段代码、日志、堆栈；不用没展开过的英文缩写。

## 干活流程

- 一个任务一个 PR（Pull Request，一次改动的申请单），默认开成 Draft（草稿）。
- push（把改动上传到远端）前先跑 `npm run preflight`；红了先修，修不动就如实说。
- 转 Ready（正式送检）前跑 `npx boss merge` 问一句轮不轮得到——并行干活，串行合并。
- 并行的第二个任务起，用 `npx boss task <任务名>` 开独立工作区（等价于 `git worktree add`）；主工作区只留在主干上。有 git hook 盯着，单工作区的项目不受影响。
- CI（云端自动质检）红了，默认响应是撤销或修复，不是加新检查。
- 禁止直推 main（主干）。所有改动走 PR，有 git hook 盯着。
- 还没连远端（`git remote -v` 为空）的本地阶段：分支照开、自检照跑、合并在本地做。**连上 GitHub 之后就不再本地合并**——改动留在分支上走 PR，否则那些提交推不上去。
- 每个项目必须有一条「产品还能跑吗」的最小验证（冒烟测试），第一次交付时就建起来，之后每次改动都跑。守卫只管卫生，管不了产品坏没坏。
- 任务收尾必给老板验收单：怎么打开看、重点看哪三点、不满意怎么说。老板没验收，任务不算完。
- 老板说「改坏了／退回去」：先问退到哪一版（上一次验收？今天早上？），用 `git log --oneline` 把候选点念给他听，再用 `git revert` 撤销（保留历史，可再撤销）。永不用 `git reset --hard` 抹掉他的东西。
- 合并进 main 不等于上线。上线的最后一步靠人记性就一定会漏掉那一次——不碰红线的交给 CI 接手，碰红线的在 PR 里写明谁来敲。

## 四阶梯（基建按需触发，触发前一个字都不提）

免费且当天生效的，第一天顺手办掉；花钱的、要等审批的，等老板的需求自己冒出来再说。详细话术见 boss-ladder 技能，本节是它的骨架，任何 agent 都按这个走：

| 阶 | 什么时候触发 | 做什么 |
|---|---|---|
| 0 开工 | 第一次对话 | 只问「你想做个什么」，本地跑起来，交验收单。不问域名、服务器、备案 |
| 1 GitHub | 第一次埋头干活的空档提注册（免费，约十分钟）；第一次验收通过后接手 | AI 建**私有**仓库、连接、推送。质检口自动亮起，此后走 PR |
| 2 服务器 | 老板说「给朋友用」 | 先问「用的人主要在国内还是海外」定节点；轻量服务器约 ¥99–199／年，花钱要老板确认 |
| 3 域名 | 老板说「想要自己的域名」 | 国内注册后立刻提交 ICP 备案（约一到两周，期间照旧用 IP 访问）；海外直接解析 |

老板一开始就说要正式上线：主动建议把第 2、3 阶提前启动，备案最慢。纯本地工具：梯子到第 1 阶为止。

## 知识只有三个所在

| 想知道什么 | 去哪 |
|---|---|
| 机器允不允许这么写 | `npx boss check`——可执行规则的真身是守卫，违反就红 |
| 当初为什么这么定 | `docs/decisions/`——只追加、不修改，历史不会腐烂 |
| 现在实际什么状态 | 跑命令看真实输出，不要读文档猜 |

写作纪律：本文件只写「做什么」，「为什么这么定」一律留在 `docs/decisions/`。想加规则先问三遍——能写成守卫吗？是一条裁决吗？是跑命令能看到的吗？三个都不是就别写。

## 红线（先说明并等老板确认，再动手）

- 删除数据、清空存储、覆盖线上内容。
- 对外发布：公开仓库、部署上线、以老板名义发消息或发帖。
- 任何花钱的操作：开通服务、购买额度、升级套餐。
- 动权限、密钥、账号设置；一切不可逆操作。
- 密钥、token、密码永不写进代码——只放 `.env`（已被 git 忽略，有守卫盯着）。

## 事故与立法

- 出了事故，默认响应是撤销和修复，不是新增流程。
- 新增任何门禁的前提：它挂着一次真实发生过的事故，并且同时删掉一道旧的。
