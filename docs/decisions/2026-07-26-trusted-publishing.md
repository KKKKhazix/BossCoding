# 发布走可信发布，不用长期令牌（2026-07-26）

## 影响

- 之前：每发一个版本，老板要亲自开终端跑 `npm publish` 并手输验证器的 6 位码。0.1.0 与 0.1.1 两次发布都是这么发的，老板反馈「好麻烦」。
- 之后：改完版本号走 PR，确认后一条 `gh workflow run publish.yml` 由流水线发布——不开终端、不输码。发布前自动跑守卫与单测，红了发不出去。

## 根因

npm 自 2026 年起收紧长期访问令牌（账号变更 2026-08、直接发布 2027-01 起受限），并把 OIDC 可信发布定为推荐路径。它的原理是 GitHub 与 npm 之间一次性握手换取短时身份，**世上不存在一个「拿到即可冒充发包」的长期密钥**——这同时消掉了发布的操作负担和最大的一处凭据风险。

前置条件本仓库恰好已满足：`package.json` 的 repository 地址必须与 GitHub 仓库一致（2026-07-26 PR #3 补齐）、必须用 GitHub 托管机器、Node ≥ 22.14 且 npm ≥ 11.5.1。

## 裁决

**发布只走 `publish.yml` 流水线（可信发布）；触发方式为手动，须老板确认后再触发。本机 `npm publish` 降级为应急退路。**

## 被否决的方案

**「在仓库里存一个自动化令牌（NPM_TOKEN）」**：同样能免验证码，但等于把一把可以冒充作者发包的长期钥匙放进仓库设置里——这正是 2026 年供应链投毒的主要入口，也正是 npm 本轮政策要淘汰的东西。安全性比现状更差，不采用。

**「合并到 main 即自动发布」**：省掉最后一次确认，但发布不可撤销（npm 不允许重发同一版本号），且与本项目「发包是红线、须先确认」的规则直接冲突。保留手动触发这一道闸。

**「维持手工 `npm publish`」**：零改动，但每次发布都要老板在场、开终端、输码——发布摩擦越大，越会攒着不发，用户拿到修复的时间就越晚。

## 不变量

1. 发布前必过 `npm run preflight`（守卫＋单测）。发布不可撤销，检验必须在发货前跑完。
2. `publish.yml` 的文件名与 npm 侧登记的信任关系绑定：**改文件名必须同步改 npm 包设置里的登记**，否则发布会以身份不匹配失败。
3. workflow 里永不出现 npm 令牌。若某天不得不用令牌（例如可信发布不可用），须先另立一篇裁决说明为何，并给出退出条件。
4. 失效条件：若 npm 取消 OIDC 可信发布或改变其身份校验方式，本裁决失效，届时按当时官方文档重估，而不是私自退回长期令牌。
