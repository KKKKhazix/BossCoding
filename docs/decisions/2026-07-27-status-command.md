# 第六个命令 status：把「我在第几阶」变成跑命令能看到的事实（2026-07-27）

## 影响

- 之前：四阶梯只写在技能文件里，也就是只活在当前那轮对话的记忆里。换个对话窗口、换台电脑、隔一周回来，老板和 AI 都无从知道项目走到哪儿了——只能读文档猜，而这套框架自己的规矩第三条就是「现在实际什么状态，跑命令看，不要读文档猜」。四阶梯是唯一一件被写进文档却没有命令能查的事。
- 之后：`npx boss status` 一句话答完：在哪一阶、干活环境齐不齐（首个提交、依赖、项目简介）、有几条并行任务、哪些任务文件夹可以回收，最后只给一条「下一步」。

## 根因

实测审查里三个独立的卡点都指向同一个缺口：新人不知道自己该干什么（init 的四步走完就断了）、AI 换会话后不知道该不该提 GitHub（四阶梯的触发条件全靠记忆）、依赖没装导致自检失败时没有任何地方能看出「环境不齐」。这三件事的共同解法不是三段文档，是一个只读命令。

## 裁决

**新增第六个命令 `boss status`：只读，探测四阶梯位置（有没有远端）与干活环境（首个提交、依赖、项目简介占位符、工作区数、可回收的旧任务），结尾只给一条此刻真正该做的下一步。**规则模板与两个技能都改成「拿不准就跑 status」，把它立为状态的唯一真身。命令面从五个变六个，本篇即那次显式立法（先例：merge 第四、task 第五）。

## 被否决的方案

**「写进技能文档，让 AI 自己探测」**：v1 就是这样，问题正是它——探测逻辑散在提示词里，各家 agent 执行力参差，而且老板本人没法自己查（他不会跑那一串 git 命令）。

**「在 AGENTS.md 里记录当前阶段」**：把会变的状态写进规则文件，恰好是 rules-budget 守卫和「知识只有三个所在」明令禁止的事——状态会腐烂，文档不会自动更新。

**「status 顺手把缺的东西补上（装依赖、建仓库）」**：只读是它可信的前提。一个会动手的 status，老板就不敢随便跑了；补依赖的活已经在 `boss task` 里（那里有明确的触发时机），建仓库是第 1 阶的动作，要老板本人参与。

## 不变量

1. `status` 永不写盘、永不联网、永不改任何文件——判据：在任何目录跑它都不会产生副作用（测试盯着）。
2. 它的每一项结论都必须来自当场跑命令的真实输出，不得读取任何声明式的「当前阶段」配置。
3. 结尾的「下一步」永远只给一条，且按最短路径排序（没提交 → 没装依赖 → 简介没填 → 连 GitHub → 照常干活）。给两条以上就等于没给。
4. 失效条件：若四阶梯本身被推翻或改写，本命令的阶段判定随之重写；若探测项增长到超过一屏，说明它在长成仪表盘，届时砍回「一阶＋环境＋一条下一步」。
