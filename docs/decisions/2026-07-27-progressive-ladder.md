# 四阶梯：基建渐进式触发，正反馈永远第一（2026-07-27）

## 影响

- 之前：框架默认用户已经备齐 GitHub 与 CI。实测小白路径：还没建远端仓库时，交付流程第 4–5 步（开 PR、`boss merge`）直接撞红墙，且报错话术把「还没走到那一步」说成「你配置坏了」；教程读者要先过完域名、服务器、备案（约一到两周等待）才敢开工。
- 之后：小白从建文件夹到第一次看到产品跑起来，中间零个基建名词；每个基建概念在它变得有用的那一刻才出现，出现时带着老板正想解决的问题。

## 根因

三个叠加的事实：

1. 目标用户的正反馈窗口极窄：先看到产品跑起来，比什么都强（上游教程 20 步的核心原则）。把最慢、最没反馈的环节（备案约 1–2 周）放在开工之前，一部分人会在第一次看到产品之前流失。
2. 各类基建的成本结构完全不同：GitHub 免费、约十分钟、当天生效，且框架的脊柱（PR 流程＋CI 质检口）全插在它上面；服务器、域名要花钱（腾讯云轻量约 ¥99–199／年），备案要等审批。把它们按同一个时点处理——无论全前置还是全后置——都至少错一半。
3. 本地迭代期可能长达数周：备份缺位（硬盘一坏全没）与质检口空转的风险随时间累积，所以 GitHub 不能等「用户想要测试流程」才出现。

## 裁决

**基建按四阶梯渐进触发：免费且当天生效的，第一天顺手办掉；花钱的或要等审批的，等老板的需求自己冒出来再触发。**具体：第 0 阶开工（第一次对话只问「你想做个什么」，本地跑起来验收）；第 1 阶 GitHub 拆两半、都落在第一天（注册塞进 AI 第一次干活的空档，连接与推送在第一次验收通过后代办，卡住不堵主线）；第 2 阶服务器（触发词「给朋友用」，此时问「用户在国内还是海外」定节点）；第 3 阶域名＋HTTPS（国内走 ICP 备案、海外免）。老板明确说「要做正式上线的产品」时跳级，提前启动最慢的备案站。产品形态只认两种：网页与纯本地工具；后者的梯子到第 1 阶为止。梯子的执行载体是 boss-ladder 技能；`boss merge` 在无远端时按本地阶段放行（退出码 0）是它在命令层的机器体现。

## 被否决的方案

**「先备齐基建再开工」（检测缺服务器／缺 GitHub 就先引导购买注册）**：把注册、付钱、审批放在用户尝到任何甜头之前，教程 20 步已实证这类前置是最大流失点；且对纯本地工具用户，服务器是永远用不上的开销。

**「第一天铺两条线」（开发线＋办证线并行，备案第一天启动）**：比前者好，但仍在用户还没做出东西时谈手续；且第一天无法回答「国内还是海外」「要不要域名」——形态还没显出来，问了也是猜。降级为跳级规则：只对明确说要正式上线的老板提前启动。

**「单机档」（无远端时静默降级，不引导升级）**：不拦路是对的，不引导是错的——用户永远停在没有备份、没有云端质检的状态里。机制被吸收（无远端不报错），定位被否决（每次降级输出必须指路下一阶）。

**「形态问卷」（第一次对话先问网页还是小程序还是工具）**：小程序整条砍掉（形态矩阵翻倍、审核流程完全不同）；网页与本地工具也不必问——做什么东西，形态自己会显出来，问卷是把分类工作推给最不懂分类的人。

## 不变量

1. 正反馈永不被基建阻塞：从 init 到第一次本地验收，路径上不得出现任何注册、付费、审批环节；`boss merge` 等命令在无远端时必须放行并指路，不得报错（测试盯着）。
2. 「还没到那一步」与「配置坏了」是两种含义不同的状态，输出必须可区分（沿用 2026-07-27-deploy-blueprint-errata 不变量 3）。
3. 每个触发信号必须是可观察的具体事件（「第一次验收通过后」「老板说给朋友用」），不许写「合适的时候」。
4. 失效条件：若真实用户反馈中出现「第一天结束仍未连上 GitHub」成为常态（注册卡死率高），或「到第 3 阶才知道要等备案」引发成规模的抱怨，按实例重估第 1／3 阶的触发点，而不是凭感觉挪。
