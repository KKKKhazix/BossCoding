# 新检查先当提醒跑一个版本，下一版才硬拦（2026-07-27）

## 影响

- 之前：守卫只有一个级别——违反就红。而用户项目按兼容范围引用本包（`^0.x`），维护者发一次新版，全网项目下次跑 CI 自动用上。这两件事叠在一起意味着：**我们每加一道检查，就单方面把一批昨天还绿、且什么都没改的仓库改红了。**
- 之后：新检查进场时只提醒（输出里的黄色 △），不影响退出码；跑满一个版本、看清真实误报率之后，下一版才转硬拦。用户有一个版本的时间从容处理。

## 根因

这个风险是框架自己的形态带来的，别的项目没有：一个只给自己用的守卫改红了自己，作者当场就修；一个发布出去的守卫改红的是**不在场的人的仓库**，他们既不知道为什么红，也没参与过那次决定。AGENTS.md 里那句「框架的用户是拿它当地基的小白，一次坏发布会同时伤到所有装了它的项目」讲的就是这件事——只是此前它只被理解成「别发坏代码」，没被理解成「别把新规矩即时生效」。

这一版一次要加三条 CI 配置检查与一条规则行长检查，逼出了这个机制：四条新检查同时硬拦，等于同时给所有用户项目加了四道新门。

## 裁决

**守卫返回的问题可带 `level: "warn"`：黄色输出、计入提醒数、不影响 `boss check` 的退出码。新增的检查一律以 warn 身份进场，下一个版本再由一次显式的 PR 改成硬拦——转硬拦是一个决定，不是一次顺手。**

## 被否决的方案

**「新检查直接硬拦，让用户自己关」**：本包没有关单条守卫的开关，用户能做的只有锁死版本或卸载。把「要么全接受要么全不要」丢给不懂的人，等于逼他们卸载——这正是 v1 不变量 3 说的「守卫被关掉比没有更糟」的更坏版本。

**「加一个配置文件，让用户逐条开关守卫」**：能解决问题，但它把「这套地基长什么样」的决定权切碎给了每个项目，而这套框架的卖点恰恰是「不用你决定」。而且带开关的守卫最终都会被关到只剩零。不采用。

**「按用户项目的引用范围做灰度」**：发一个 `0.x.0-beta` 让愿意的人先试。想法对，但目标用户是小白，他们不会去装 beta，灰度池实际为空。不采用。

## 不变量

1. 一次发布不得让「用户什么都没改的仓库」从绿变红。新检查以 warn 进场是这条的机器体现。
2. warn 只给新检查用，不是「拿不准就 warn」的垃圾桶。一条检查若一个版本后仍不敢转硬拦，说明它误报没收敛，该删掉而不是继续挂着提醒。
3. 转硬拦必须是独立一次 PR，正文写明它当提醒跑了哪个版本、期间收到过什么反馈。
4. 失效条件：若出现「用户长期无视黄色提醒、转硬拦时照样一片红」的实例，说明宽限期没起作用，届时改为在提醒里写明「下一版将硬拦」的具体版本号并重估本篇。
