# 第五个命令 task：把「开并行任务」收成一个按钮（2026-07-27）

## 影响

- 之前：并行开工的正确姿势（`git worktree add` 独立工作区）靠 agent 记得、会用；小白最常见的并行姿势是「同一个文件夹开两个对话窗口」——此时工作区数是 1，主工作区保护 hook 按误报收敛设计恰好不激活（它只在 ≥2 个工作区时出声），保护在最需要它的场景里休眠。上游真实事故：两个 agent 同一工作区 37 分钟内 7 次互相切分支，没丢代码纯属侥幸。
- 之后：老板说「开个新任务」，AI 跑 `npx boss task <任务名>`，一条命令得到独立工作区＋任务分支＋一句人话指引（把新文件夹拖进新的 AI 对话窗口）；工作区数随之 ≥2，既有保护自动激活。

## 根因

「无脑开工作树发任务」是本框架对老板的核心承诺，但它此前没有按钮：worktree 的目录放哪、分支叫什么、从哪条主干出发、开完之后老板该干什么，每一项都靠各家 agent 自由发挥。能力参差的 agent 里总有发挥错的；而放错位置的 worktree（嵌进仓库里）还会污染 git 状态。命令把这些自由度收掉，姿势唯一化。

## 裁决

**新增第五个命令 `boss task <任务名>`：在主工作区旁边开 `<仓库名>-<任务名>` 目录、建 `lane/<任务名>` 分支（基于主干），打印「拖进新对话窗口」的下一步指引与合并后的清理命令。只建不删——删工作区是破坏性动作，交还给人。**命令面从四个变五个，本篇即那次显式立法（先例：merge 是第四个，见 2026-07-27-serial-merge-as-a-command）。

## 被否决的方案

**「写进技能文档，教 agent 手动 worktree add」**：v1 就是这么做的，问题正是它——文案约束依赖执行力，没有幂等、没有防呆（分支重名、目录已存在、还没有首个提交），错误发生在老板看不懂的层面。

**「命令顺带删工作区（task --done）」**：删除是破坏性动作，与「只读判定」的 merge、「绝不覆盖」的 init 同一条纪律相抵触；清理命令在输出末尾给出，由人执行。

**「自动起分支名不加 lane/ 前缀」**：前缀让并行任务在分支列表里天然分组，且与本仓库自身的实践一致；不值得为省四个字符放弃可读性。

## 不变量

1. `boss task` 只创建、不删除、不覆盖：目录已存在、分支已存在时明确报错并给修法，绝不清场重来（测试盯着）。
2. 新工作区永远在主工作区**旁边**（同级目录），不嵌进仓库内部——嵌进去会被 git 当成未追踪文件。
3. 失效条件：若某类宿主（如网页版 agent）没有「拖文件夹开新会话」的形态导致指引失效，按当时的宿主形态改写输出文案，命令本体不变。
