# 主工作区只跑主干，用 git hook 执行（2026-07-27）

## 影响

- 之前：「并行开发用独立工作区」只是规则文件里的一句话。上游 aihot 实测：两个 agent 同时在主工作区各自开分支干活，reflog 记下 37 分钟内 7 次分支切换；没丢代码纯属两边改的文件不重叠——真撞上时 git 会把未提交的改动安静地带去别人的分支或直接换掉，**不报任何错**。规则在、工具在（机器上有 18 个独立工作区），没有任何东西执行它。
- 之后：`boss init` 和 `boss update` 会装两个 git hook，切分支时提醒、真要提交时硬拦。只有仓库已经开了 ≥2 个工作区才启用，所以对 BossCoding 的默认用户（单人、单工作区）**零可见变化、零误报**。

## 根因

这条只能在本地拦：工作区状态不进 git，CI 拿到的是树和提交，看不出「这笔是在哪个工作区切出来的」。写成守卫（`boss check`）无从判断，写进 CI 更无从判断——所以它是这套框架里第一件不走守卫的强制。

判据不能用路径约定（每个人给工作区起的名字都不一样），用 git 自己的两个目录：`git rev-parse --absolute-git-dir` 与 `--git-common-dir` 在 linked worktree 里不同、在主工作区里相同。

## 裁决

**「主工作区只跑主干」由 `pre-commit`＋`post-checkout` 两个 hook 执行，同一份脚本挂两处（靠 `$0` 的文件名分工）；仅当仓库已有 ≥2 个工作区时启用，逃生阀用 git 内置的 `--no-verify`，不另造旁路。**

- `post-checkout` 只提醒：切分支那一刻改正成本为零，且 git 本来就忽略这个 hook 的退出码。
- `pre-commit` 硬拦，报错里直接给出两条出路（开独立工作区／`git stash` 带走改动）。
- 主干分支名从仓库读（`origin/HEAD` → `main` → `master`），不假设一定叫 main；detached HEAD（rebase／bisect 中途）放行；`CI` 环境变量存在时整体闭嘴。
- 安装时显式 `chmod +x`：**git 会静默忽略没有执行位的 hook**（实测复现：第一次测试根本没拦住）。测试因此用真 `git commit` 验证拦截，不直接跑脚本——要证的正是「git 会不会执行它」。
- 绝不覆盖别人的 hook（husky、lefthook、手写的都算）：只认自己写的标记行 `bosscoding:main-worktree-guard`，位置被占就让路并提示。

## 被否决的方案

**「照抄上游：装上就一律拦」**：上游 aihot 是多 agent、18 个工作区的形态，那里「主工作区上有分支」必然是事故。BossCoding 的默认画像是单人单 agent，而框架自己的技能第 2 步就写着「从 main 开一条新分支」——一律拦等于第一天就拦死自己教的流程。误报多的守卫会被用户关掉，比没有更糟（v1 不变量 3）。改成「有 ≥2 个工作区才启用」：用户没开工作区就说明没在并行，风险不存在；开了就说明已经采用这套姿势，此时主工作区上的分支提交才是那次事故。

**「写成守卫进 `boss check`」**：CI 看不到工作区状态，守卫在 CI 里必然全绿或必然误报，两种都无价值。

**「挂 `npm postinstall` 自动补装」**（上游的做法）：能覆盖「clone 出新副本后 hook 是裸的」这个缺口，但用户项目若是要发布到 npm 的库，它的 postinstall 会在下游安装者机器上执行，那里既没有 AGENTS.md 也可能没有 `boss` 命令，一次失败就是别人 `npm install` 报错。代价落在与本项目无关的第三方身上，不采用。缺口改由 `boss update` 补装 + README 写明「重新 clone 后跑一次」。

**「设 `core.hooksPath` 指向仓库内的目录」**：hook 能进版本库、clone 即生效，但这个配置全仓唯一，一设就顶掉用户已有的 husky／lefthook。安装一个流程地基不该悄悄拆掉别人的地基，不采用。

## 不变量

1. 这个 hook 在单工作区的仓库里必须完全无声——它是并行开发的护栏，不是给单人流程加的门。判据：`git worktree list` 只有一行时任何路径都 `exit 0`，有测试盯着。
2. 装 hook 永不覆盖非 BossCoding 写的文件；认领靠标记行 `bosscoding:main-worktree-guard`，有测试盯着。
3. 逃生阀只用 git 内置的 `--no-verify`。框架不自造开关、不设环境变量旁路——多一条旁路就多一条没人知道的绕行路。
4. 装完必须显式 `chmod +x`，且拦截行为用真 `git commit` 验证。只跑脚本本身的测试会在「hook 没执行位」时依然全绿，那正是这条要防的失效。
5. 失效条件：若出现「单工作区用户仍被这个 hook 打扰」的真实反馈，说明 ≥2 工作区的判据不成立，届时按真实案例重估而不是加开关；若 BossCoding 用户中始终没有多 agent 并行的实例（见 issue #2 的触发条件），本 hook 连同这篇一起可以整体删掉。
