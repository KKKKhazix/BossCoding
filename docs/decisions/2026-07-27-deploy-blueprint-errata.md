# 勘误：「合并不等于上线」里那份部署蓝图有三个坑（2026-07-27）

（对应 issue #9，勘误对象是 `2026-07-27-merge-is-not-release.md` 里被否决方案一节记下的那份 CI 内嵌 deploy 蓝图。决策档案只追加不修改，所以勘误另开一篇。）

## 影响

- 之前：那份蓝图被记成「上游已验证可行，只是不适合进框架」。照它原样实现会连踩三个坑、修三轮。
- 之后：蓝图仍然不进框架（原裁决不变），但档案里留下了它的三个坑与两条通用教训，将来任何人（包括我们自己）照着做时不必再踩一遍。

## 根因

三个坑各自的机理：

1. **deploy job 不能待在 CI 自己的 run 里**：部署前置检查按「成功的运行」反查制品，而 deploy job 所在的运行要等 deploy 结束才可能变成功——**它在等自己**，等待时长调多大都没用。通用教训：`needs:` 保证的是「上游 job 成功」，不是「上游 run 已完成」；依赖 run 级状态（制品列表、run 结论）的动作不能待在同一个 run 里。
2. **按改动面跳过构建 ＋ 按部署位点判「该有制品」＝ 基线错配**：前者的基线是上一次合并，后者的基线是上次真正上线的位点。生产落后一笔，两个基线就错开，且**无法补救**——那棵树的制品从没被构建过，重跑 CI 仍判定不构建。解法是默认分支上每次 push 都构建，代价实测约每月 $0.2，换来「默认分支上任何一笔随时可部署」。
3. **搬 job 时 permissions 不跟着走**：拆成独立 workflow 后只剩顶层 `contents: read`，列制品要的 `actions: read`、读结论要的 `checks: read` 全丢；403 被 `2>/dev/null || return 1` 吞掉后，**与「制品不存在」显示为同一句话**，查了两轮才定位。搬一个 job ＝ 搬 steps ＋ permissions ＋ concurrency ＋ environment ＋ 触发条件，五件套一个都不能少。

这三次里出现了两次同一个模式：**把两种含义不同的失败压成了同一个空结果**——「还没到」vs「不会来」、「没权限看」vs「不存在」。

## 裁决

**框架仍不提供部署模板（原裁决不变）。三个坑里能机器化的两条（`workflow_run` 必须筛结论、必须显式 checkout `head_sha`）收进 `ci-known-traps` 守卫；不能机器化的两条（搬 job 的五件套、每次 push 都构建）留在本篇备查。「不把两种含义不同的失败压成同一个空结果」作为写错误提示的纪律，在本仓库以代码体现：`boss merge` 把「私有仓库要令牌」「被限速」「连不上网」分成三句不同的话，绝不合并成一句「查不到」。**

## 被否决的方案

**「既然坑都摸清了，就把修好的部署蓝图收进模板」**：坑摸清了不改变 `2026-07-27-merge-is-not-release.md` 的判据——框架用户里写库、写脚本、做静态站的根本没有部署这一步，且 `templates/ci.yml` 的契约是只读质检。三轮修正只是让那份实现变对，没让它变通用。

**「把三个坑写进规则模板」**：违反同一版立的写作纪律（规则文件只写「做什么」，见 `2026-07-27-rules-say-what-not-why.md`），而且它们只对「项目里有部署」这一种形态成立。留在决策档案是正确位置。

**「关掉 issue 就算了」**：这三条是花了三轮真金白银换来的，且下次实现部署时一定还会用到。issue 会腐烂，档案不会。

## 不变量

1. `templates/ci.yml` 只做质检不做部署，`permissions: contents: read` 是这条的机器体现——沿用原篇不变量 2。
2. 依赖 run 级状态（制品列表、run 结论）的动作永不与被依赖的 run 同处一个 run。
3. 错误提示不得把含义不同的失败压成同一句话。判据：读到这句话的人能否据此知道下一步该做什么——不能就是压扁了。
4. 失效条件：若框架用户中出现「按『合并不等于上线』做了但不知道怎么做」的真实实例（原篇不变量 4 的触发条件），届时把本篇的三个坑一起写进那份操作指引。
