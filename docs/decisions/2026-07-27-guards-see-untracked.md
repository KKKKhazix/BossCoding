# 守卫要看没提交的文件，否则那个「绿」是假的（2026-07-27）

## 影响

- 之前：守卫只扫 git 已追踪的文件。实测：在全新项目里放一把明文密钥（config.js 里一行 `API_KEY="sk-live-…"`），`boss check` 回答「9 项守卫全部通过」——而 init 的第 2 步恰恰教新人此刻跑一次检查。**新人学到的第一课是「绿等于安全」，而那个绿是「什么都没看」的绿。**
- 之后：密钥守卫连未追踪、未被忽略的文件一起扫，那把密钥当场被抓；`boss check` 的结论后面附上「扫了 N 个文件」，空目录另给一句黄色提醒——「绿」从此可以被追问一句「你看了什么」。

## 根因

守卫用 `git ls-files` 取文件清单，是为了拿到一份确定的、跨环境一致的名单（不受本地垃圾文件影响）。这个理由对文档类守卫成立，对密钥守卫不成立：**密钥的危害在于「写下来了」，不在于「提交了」**。而新项目的第一天恰好是密钥最容易被粘进代码的时刻（照着教程配 API），也恰好是文件全都还没提交的时刻——守卫最该睁眼的那一刻，它闭着眼。

扩面不会伤到任何人的 CI：CI 跑的是干净检出，工作区里没有未追踪文件，扫描面与之前完全相同。也就是说这次改动只让本地更早发现问题，不会把任何仓库从绿改红——不触发「新检查以 warn 进场」那条纪律的适用条件。

## 裁决

**上下文新增 `workingFiles()`（已追踪 ＋ 未追踪且未被 .gitignore 忽略），密钥守卫改用它；未追踪的密钥文件报「没有被忽略，下次 git add 就会被收进版本库」，与已追踪的报法分开。`boss check` 的通过结论必须带上扫描文件数，扫到 0 个文件时额外给一句「这不代表安全」的黄色提醒。**其余守卫维持只看已追踪文件——文档卫生类问题在提交后再报为时不晚，扩面只会增加噪音。

## 被否决的方案

**「所有守卫一起扩面」**：文档链接、裸待办这类守卫扫未提交文件只会制造噪音（草稿、临时笔记），违反「误报多的守卫会被关掉，比没有更糟」。

**「未追踪文件的问题只报 warn」**：符合「不把别人的绿改红」的纪律，但这里没有绿要保护（CI 检出没有未追踪文件），而一把明文密钥报成黄色提醒会被无视——密钥这一类不存在「先观察一个版本」的余地。

**「让 init 提示新人先提交再检查」**：把机器该做的事推给最不懂的人，且他就算提交了，下一把密钥还是会在提交前被写下来。

## 不变量

1. `boss check` 报「通过」时必须同时报出扫了多少文件；扫到 0 个必须明说这不代表安全（测试盯着）。
2. 扩面永不包含被 .gitignore 忽略的路径——否则 node_modules 会把扫描面撑爆。
3. 密钥守卫对「写下来了」负责，不对「提交了」负责；判据：一把刚粘进新文件的密钥，在任何提交动作之前就该被抓住。
4. 失效条件：若出现未追踪文件带来成规模误报的真实实例，按实例收窄（例如只扫特定后缀），而不是退回只看已追踪。
