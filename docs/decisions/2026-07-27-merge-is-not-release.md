# 合并不等于上线（2026-07-27）

## 影响

- 之前：规则文件把流程写到「CI 绿了就合并」为止，上线的最后一步（部署、发包）没人管。上游 aihot 实测：三个 PR 合并后生产环境静默落后**一整天**，由用户主动发问才发现；当天修完**又立刻复现一次**。
- 之后：规则模板多一行裁决——合并进 main 不等于上线，最后一步不许挂在人的记性上。装了 BossCoding 的项目在写流程时会被迫回答「谁来敲最后那一下」。

## 根因

`gh pr merge --auto` 交代完就返回，**真正的合并发生在数分钟后 CI 转绿的那一刻**——那时发起合并的会话通常已经结束。没有任何触发器接手最后一步，唯一的检测手段是有人碰巧想起来查。

这对任何「agent 负责合并、人不在场」的流程都成立，与项目形态无关，所以它属于框架而不属于某个项目。

但**解法不通用**：上线动作能否自动，取决于它在该项目是不是红线。aihot 的部署是日常动作，可以让 CI 接手（已在上游 #618 落地）；BossCoding 的上线是 npm 发包，是写进规则的红线，必须老板确认——同一条原则在两个项目里落成相反的实现。所以能进框架的只有那句判断标准，不是那套改造。

## 裁决

**规则模板只收一句裁决：「合并进 main 不等于上线，不碰红线的交给 CI 接手，碰红线的在 PR 里写明谁来敲。」部署自动化的具体实现留在各自项目，框架不提供、不假设、不检查。**

## 被否决的方案

**「把 deploy job 加进 `templates/ci.yml`」**：上游已验证可行，但它假设用户项目有服务器要部署。框架用户里写库、写脚本、做静态站的根本没有这一步，模板里凭空多出一个部署任务对他们全是噪音；且 `templates/ci.yml` 的契约是只读质检（`permissions: contents: read`），加部署要给它写权限和密钥，把一个安全的默认值改成危险的默认值。不采用。

**「写成守卫，检查项目有没有配部署触发器」**：守卫无法判断一个项目该不该有上线动作，绝大多数项目会被误报。违反 v1 不变量 3（误报多的守卫会被用户关掉，比没有更糟）。不采用。

**「只留 issue，不进规则」**：issue 会腐烂——三个月后没人记得它为什么还开着，而这条教训每次新项目起流程时都用得上。issue 是待办的载体，不是裁决的载体。不采用。

**「照抄那三条密钥收窄进模板」**（专用密钥、受保护环境、主机指纹从服务器读出而非 `ssh-keyscan`）：都是实测有效的正确做法，但只对「CI 要 SSH 进生产机」这一种形态成立。留在本篇作为将来实现时的参考，不进用户规则。

## 不变量

1. 上线动作是否交给机器自动触发，由它在该项目是不是红线决定；**红线动作永不自动触发**，规则模板的红线一节是这条的真身。
2. `templates/ci.yml` 只做质检不做部署，`permissions: contents: read` 是这条的机器体现——任何要求给它写权限或密钥的改动都要先推翻本篇。
3. 框架收的是判断标准，不是某个项目的改造方案。判据：换一个形态完全不同的项目（无服务器、无发布物），这句话还成立吗？不成立就不进模板。
4. 失效条件：若 BossCoding 用户反馈中出现「按这句话做了但不知道怎么做」的实例，说明只给判断标准不够，届时按真实案例补一份操作指引（放 `docs/`，不放规则文件）；若发包不再是红线，本仓库 AGENTS.md 那条随之重写。
